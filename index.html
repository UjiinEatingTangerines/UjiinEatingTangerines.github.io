문제 Problem 課題

크레딧 적립·사용·차감 처리 시 동시 요청에서 잔액 정합성이 깨지는 케이스가 간헐적으로 발생. 또한 내부 서비스마다 크레딧 연동 방식이 제각각이라 신규 서비스 통합 시 매번 2주 이상의 연동 개발이 필요.

Intermittent balance inconsistencies occurred when concurrent requests hit the credit earn/use/deduct flow. Additionally, each internal service integrated with the credit system differently, requiring over two weeks of custom development for every new integration.

クレジットの付与・使用・差引処理で同時リクエストにより残高整合性が崩れるケースが散発的に発生。さらに内部サービスごとにクレジット連携方式がバラバラで、新規サービス統合のたびに2週間以上の連携開発が必要だった。

해결 과정 Solution 解決プロセス

  • 비관적 락 + 트랜잭션 경계 재설계로 잔액 정합성 확보. 기존 낙관적 락은 충돌 시 재시도 로직이 누락된 상태에서 잔액 불일치를 유발. 적립·사용·차감을 단일 트랜잭션으로 묶고 SELECT FOR UPDATE로 잔액 행을 잠가 동시성 문제를 근본 차단. 분산 락(Redis)은 크레딧 특성상 단일 DB 내 정합성이면 충분하여 운영 복잡도 대비 이점 없음.
  • QueryDSL 기반 동적 조회로 이력 조회 성능 확보. 기간·유형·상태 등 복합 조건 조회가 잦은데, MyBatis 동적 SQL은 조건 조합 폭증 시 XML 유지보수가 어려워 QueryDSL로 전환. 커버링 인덱스와 조합하여 이력 조회 p95 응답속도 개선.
  • SDK 패키징으로 연동 비용 제거. API 경계(boundary)를 명확히 정의하고 클라이언트 SDK를 GitHub Packages / Nexus로 배포. 서비스별 직접 HTTP 연동을 SDK 의존성 추가로 대체.
  • Pessimistic locking + transaction boundary redesign to ensure balance consistency. The existing optimistic lock was causing balance mismatches because retry logic was missing on conflict. Wrapped earn/use/deduct in a single transaction with SELECT FOR UPDATE to lock the balance row, eliminating concurrency issues at the root. A distributed lock (Redis) was unnecessary since single-DB consistency was sufficient for credit operations, and would only add operational complexity.
  • QueryDSL-based dynamic queries to improve history lookup performance. Complex condition queries combining period, type, and status were frequent; MyBatis dynamic SQL became unmaintainable as condition combinations grew. Switched to QueryDSL and combined with covering indexes to improve history query p95 response time.
  • SDK packaging to eliminate integration cost. Defined clear API boundaries and published client SDKs to GitHub Packages / Nexus, replacing per-service direct HTTP integration with a single SDK dependency.
  • 悲観的ロック＋トランザクション境界再設計で残高整合性を確保。 既存の楽観的ロックは衝突時のリトライロジックが欠落しており残高不整合を誘発。付与・使用・差引を単一トランザクションにまとめSELECT FOR UPDATEで残高行をロックし同時性問題を根本的に遮断。分散ロック（Redis）はクレジット特性上、単一DB内の整合性で十分であり運用複雑度に見合うメリットなし。
  • QueryDSLベースの動的クエリで履歴照会性能を確保。 期間・種別・状態など複合条件照会が頻繁で、MyBatis動的SQLは条件組み合わせ増加時にXMLの保守が困難になりQueryDSLへ移行。カバリングインデックスと組み合わせ履歴照会p95応答速度を改善。
  • SDKパッケージングで連携コストを除去。 API境界を明確に定義しクライアントSDKをGitHub Packages/Nexusで配布。サービスごとの直接HTTP連携をSDK依存追加に置き換え。

문제 Problem 課題

일별 정산 집계를 단일 쿼리로 처리하던 구조에서 결제 트랜잭션 증가에 따라 배치 수행 시간이 선형 증가, 야간 배치 윈도우를 초과하기 시작. 정산 오류 발생 시 수동 재처리로 익영업일까지 지연되는 운영 리스크 존재.

Daily settlement aggregation relied on a single query, and batch execution time grew linearly as payment transactions increased, eventually exceeding the nightly batch window. Settlement errors required manual reprocessing that was delayed until the next business day, creating operational risk.

日次精算集計を単一クエリで処理していた構造で、決済トランザクション増加に伴いバッチ実行時間が線形増加し夜間バッチウィンドウを超過し始めた。精算エラー発生時は手動再処理で翌営業日まで遅延する運用リスクが存在。

해결 과정 Solution 解決プロセス

  • Spring Batch Chunk 기반 분할 처리로 배치 시간 단축. 단일 대량 쿼리를 MyBatis Cursor + Chunk 처리로 전환하여 메모리 사용량을 일정하게 유지하면서 처리량 확보. Partitioning은 정산 특성상 날짜 단위 순차 정합이 필요하여 Chunk 단위 처리가 적합.
  • SQS + EventBridge로 비동기 이벤트 기반 정산 트리거 구축. 결제 완료 이벤트를 SQS로 수신하고, EventBridge 스케줄로 일별·월별 정산 Job을 트리거. 수동 크론 관리를 제거하고 재처리 시 SQS DLQ에서 실패 이벤트를 자동 재투입.
  • 대사(reconciliation) 로직을 별도 Step으로 분리. 정산 집계와 대사를 하나의 Job 내 별도 Step으로 구성하여, 대사 실패 시 집계 롤백 없이 대사 Step만 재실행 가능하도록 설계.
  • Spring Batch chunk-based processing to reduce batch time. Replaced the single bulk query with MyBatis Cursor + chunk processing to keep memory usage constant while maintaining throughput. Partitioning was unsuitable because settlement requires date-sequential consistency, making chunk-level processing the right fit.
  • SQS + EventBridge for async event-driven settlement triggers. Payment completion events are received via SQS, and EventBridge schedules trigger daily/monthly settlement jobs. Eliminated manual cron management; on failure, events are automatically re-ingested from the SQS DLQ.
  • Separated reconciliation logic into a dedicated Step. Structured aggregation and reconciliation as separate Steps within a single Job so that reconciliation failures can be retried without rolling back the aggregation.
  • Spring Batch Chunkベース分割処理でバッチ時間を短縮。 単一大量クエリをMyBatis Cursor＋Chunk処理へ転換しメモリ使用量を一定に保ちながらスループットを確保。Partitioningは精算特性上、日付単位の順次整合が必要なためChunk単位処理が適切。
  • SQS＋EventBridgeで非同期イベントベースの精算トリガーを構築。 決済完了イベントをSQSで受信し、EventBridgeスケジュールで日次・月次精算Jobをトリガー。手動cron管理を排除し、失敗時はSQS DLQから自動再投入。
  • 対査（reconciliation）ロジックを別Stepとして分離。 精算集計と対査を1つのJob内の別Stepとして構成し、対査失敗時に集計をロールバックせず対査Stepのみ再実行可能に設計。

통합 메시징 플랫폼 구축 (프로젝트 리드) Unified Messaging Platform (Project Lead) 統合メッセージングプラットフォーム構築（プロジェクトリード） Kotlin, Spring Boot, JPA, gRPC, Protobuf, MQTT(EMQX), GitHub Packages

SMS, LMS, 앱 푸시, 이메일, 알림톡 등 13개 이상의 서비스에서 각자 벤더 API를 직접 호출하는 구조로 운영. 채널 추가·벤더 변경 시 전 서비스 수정이 필요하고, 발송량 제어가 불가능하여 비용 초과 및 장애 전파 리스크 상존.

Over 13 services were each directly calling vendor APIs for SMS, LMS, push notifications, email, and KakaoTalk alerts. Adding a channel or switching a vendor required changes across all services, and there was no send-volume control, leading to cost overruns and cascading failure risk.

SMS、LMS、アプリプッシュ、メール、アリムトークなど13以上のサービスがそれぞれベンダーAPIを直接呼び出す構造で運用。チャネル追加・ベンダー変更時に全サービスの修正が必要で、送信量制御が不可能なためコスト超過と障害伝播リスクが常在。

문제 Problem 課題

파편화된 메시징 구조 자체가 문제. 개별 서비스가 벤더를 직접 호출하는 한 채널 통제와 장애 격리가 불가능.

The fragmented messaging architecture itself was the problem. As long as individual services called vendors directly, channel governance and fault isolation were impossible.

断片化されたメッセージング構造そのものが問題。個別サービスがベンダーを直接呼び出す限りチャネル統制と障害隔離は不可能。

해결 과정 Solution 解決プロセス

  • 멀티모듈 구조로 채널 추상화 계층 설계. 벤더 연동(세종텔레콤, Firebase FCM, AWS SES)을 채널 어댑터 모듈로 분리하여, 벤더 교체 시 어댑터만 교체하면 되는 구조 확보. 서비스 코드에서 벤더 의존성을 완전 제거.
  • 서비스별 일일·월별 Rate Limit 정책 수립. 13개 서비스의 과거 발송량을 분석하여 피크 볼륨 대비 배수로 쿼터를 산정. 월초 배치 패턴 서비스는 일일 한도를 별도 상향, 버스트 특성 서비스는 Token Bucket에 30% 버스트 헤드룸 적용.
  • MQTT 브로커(EMQX)를 디스패치 레이어로 도입, Kinesis와 역할 분리. 기존 Kinesis는 데이터·로그 파이프라인으로 유지하고, 메시지 발송 디스패치는 EMQX(ECS)로 분리. Kinesis에 디스패치를 태우면 로그 파이프라인과 발송 트래픽이 결합되어 장애 전파 위험. MQTT의 토픽 기반 라우팅이 채널별 발송 분기에 적합.
  • gRPC/Protobuf 기반 내부 SDK를 GitHub Packages로 배포. REST 대비 페이로드 크기와 직렬화 비용 절감. 서비스 측은 SDK 의존성 추가만으로 메시징 연동 완료.

  • Per-service daily/monthly rate limit policies. Analyzed historical send volumes across 13 services to set quotas at a multiple of peak volume. Batch-pattern services received elevated daily limits; burst-heavy services got Token Bucket with 30% burst headroom.
  • MQTT broker (EMQX) as the dispatch layer, separated from Kinesis. Kept Kinesis for data/log pipelines and routed message dispatch through EMQX (on ECS). Combining dispatch with Kinesis would couple log pipelines to send traffic, risking cascading failures. MQTT's topic-based routing is a natural fit for per-channel dispatch branching.
  • gRPC/Protobuf-based internal SDK published to GitHub Packages. Reduced payload size and serialization cost compared to REST. Services complete messaging integration by adding a single SDK dependency.
  • マルチモジュール構造でチャネル抽象化レイヤーを設計。 ベンダー連携（セジョンテレコム、Firebase FCM、AWS SES）をチャネルアダプターモジュールとして分離し、ベンダー交替時にアダプターだけ差し替える構造を確保。サービスコードからベンダー依存を完全除去。

전자금융업 등록 요건상 크레딧·마일리지 시스템을 폐쇄망(망분리)으로 이관해야 하는데, 레거시 API에 N+1 쿼리와 비효율 인덱스가 다수 존재하여 이관 후 제한된 인프라 자원에서 SLO 달성이 불가능한 상태.

The credit and mileage systems had to be migrated to an air-gapped (network-segregated) environment to meet e-finance registration requirements. However, the legacy API had widespread N+1 queries and inefficient indexes, making SLO compliance impossible on the constrained infrastructure after migration.

電子金融業登録要件によりクレジット・マイレージシステムを閉域網（ネットワーク分離）へ移行する必要があったが、レガシーAPIにN+1クエリと非効率インデックスが多数存在し、移行後の制限されたインフラ資源ではSLO達成が不可能な状態だった。

해결 과정 Solution 解決プロセス

  • N+1 쿼리 제거 및 Fetch Join 전환. JPA 엔티티 연관관계 로딩 전략을 재설계하여 주요 조회 API의 쿼리 수를 대폭 감소. LAZY 로딩 후 루프 내 추가 쿼리가 발생하던 패턴을 Fetch Join 또는 @EntityGraph로 일괄 전환.
  • QueryDSL 기반 동적 쿼리 리팩터링 및 인덱스 재설계. MyBatis XML로 관리되던 복합 조건 쿼리를 QueryDSL로 마이그레이션하면서, 실행 계획 분석 기반으로 복합 인덱스를 재구성.
  • 무중단 DB 마이그레이션 전략 설계·실행. 데이터 정합성 검증 스크립트를 사전 작성하고, 단계적 트래픽 스위칭(읽기 전환 → 쓰기 전환)으로 다운타임 없이 전환 완료. 롤백 시나리오별 절차서를 사전 수립.
  • Eliminated N+1 queries and switched to Fetch Join. Redesigned JPA entity association loading strategies to drastically reduce query counts on key lookup APIs. Converted patterns where LAZY loading triggered additional queries inside loops to Fetch Join or @EntityGraph.
  • QueryDSL-based dynamic query refactoring and index redesign. Migrated complex-condition queries from MyBatis XML to QueryDSL, and rebuilt composite indexes based on execution plan analysis.
  • Designed and executed a zero-downtime DB migration strategy. Pre-built data consistency verification scripts and completed the migration via phased traffic switching (read switchover → write switchover) with zero downtime. Prepared rollback runbooks for each failure scenario.
  • N+1クエリ除去およびFetch Joinへの転換。 JPAエンティティの関連関係ローディング戦略を再設計し主要照会APIのクエリ数を大幅削減。LAZY ローディング後ループ内で追加クエリが発生するパターンをFetch Joinまたは@EntityGraphへ一括転換。
  • QueryDSLベースの動的クエリリファクタリングおよびインデックス再設計。 MyBatis XMLで管理されていた複合条件クエリをQueryDSLへ移行しながら、実行計画分析に基づき複合インデックスを再構成。
  • 無停止DBマイグレーション戦略の設計・実行。 データ整合性検証スクリプトを事前作成し、段階的トラフィックスイッチング（読み取り転換→書き込み転換）でダウンタイムゼロで移行完了。ロールバックシナリオ別手順書を事前策定。

문제 Problem 課題

크레딧 만료 처리가 체계화되지 않아 만료 대상 크레딧이 잔액에 그대로 남아 있는 상태. 금결원 보고 시 낙전수입 인식 시점이 불명확하여 재무 보고 정확성에 리스크 발생.

Credit expiration was not systematized, leaving expired credits sitting in user balances. The timing of windfall revenue recognition was ambiguous during KFTC (Korea Financial Telecommunications & Clearings Institute) reporting, creating financial reporting accuracy risk.

クレジット満了処理が体系化されておらず、満了対象クレジットが残高にそのまま残っている状態。金決院報告時の雑収入認識タイミングが不明確で財務報告の正確性にリスクが発生。

해결 과정 Solution 解決プロセス

  • Spring Batch 일별 만료 스캔 Job 구현. 만료일 도래 크레딧을 Chunk 단위로 스캔하여 상태 전환 처리. 실시간 이벤트 방식은 만료일 시점에 서비스 장애 시 누락 위험이 있어, 배치 스캔 방식이 정합성 보장에 유리.
  • 만료 → 낙전수입 계정 전환 로직을 회계 기준과 정합. 만료 처리 시점에 낙전수입 계정으로의 전환이 회계 인식 기준과 일치하도록 비즈니스 로직을 설계. 재무팀과 인식 시점 기준을 사전 합의하여 보고 시 해석 차이 제거.
  • EventBridge 스케줄링 + 감사 로그로 추적 체계 확보. 배치 실행 주기를 EventBridge로 관리하고, 만료 처리 건별 감사(audit) 로그를 기록하여 금결원 보고 시 건별 추적 가능한 데이터 체계 구축.
  • Daily expiration scan Job with Spring Batch. Scans credits reaching their expiration date in chunks and transitions their status. A real-time event approach risks missing expirations if the service is down at the exact moment, so batch scanning is safer for consistency.
  • Aligned expiration → windfall revenue account transfer logic with accounting standards. Designed business logic so the transfer to the windfall revenue account matches accounting recognition criteria. Pre-aligned recognition timing with the finance team to eliminate reporting interpretation differences.
  • EventBridge scheduling + audit logs for traceability. Managed batch execution cycles through EventBridge and recorded per-item audit logs for each expiration, building a data trail traceable at the individual record level for KFTC reporting.
  • Spring Batch日次満了スキャンJobを実装。 満了日到来クレジットをChunk単位でスキャンし状態遷移処理。リアルタイムイベント方式は満了時点のサービス障害で漏れリスクがあり、バッチスキャン方式が整合性保証に有利。
  • 満了→雑収入勘定への振替ロジックを会計基準と整合。 満了処理時点での雑収入勘定への振替が会計認識基準と一致するようビジネスロジックを設計。財務チームと認識時点の基準を事前合意し報告時の解釈差異を排除。
  • EventBridgeスケジューリング＋監査ログで追跡体系を確保。 バッチ実行周期をEventBridgeで管理し、満了処理の件別監査（audit）ログを記録して金決院報告時に件別追跡可能なデータ体系を構築。

JIRA 티켓 정량 감소를 통한 업무 집중도 향상 JIRA Ticket Reduction for Engineering Focus JIRAチケット定量削減によるエンジニア集中度向上 Spring Boot, Spring Batch, AWS SQS, EventBridge

개발팀의 JIRA 티켓을 유형별로 분석한 결과, 전체 티켓의 상당수가 데이터 보정, 수기 발송, 설정 변경 등 반복 운영성 요청. 엔지니어가 핵심 개발이 아닌 운영 대응에 시간을 소모하는 구조가 문제.

Categorizing the dev team's JIRA tickets by type revealed that a large share were repetitive operational requests: data corrections, manual dispatches, configuration changes. Engineers were spending time on operational responses instead of core development.

開発チームのJIRAチケットを類型別に分析した結果、全体の相当数がデータ補正、手動発送、設定変更など反復的な運用要請。エンジニアが核心的な開発ではなく運用対応に時間を消耗する構造が問題だった。

문제 Problem 課題

티켓 수 자체가 많은 게 아니라, 자동화되지 않은 수동 작업이 티켓으로 유입되는 구조가 문제.

The issue was not the ticket volume per se, but the structure that funneled un-automated manual work into tickets.

チケット数自体が多いのではなく、自動化されていない手作業がチケットとして流入する構造が問題。

해결 과정 Solution 解決プロセス

  • 티켓 유형별 발생 빈도 분석 후 자동화 대상 선정. 최근 6개월 티켓을 카테고리별로 분류하여 상위 반복 유형을 도출. 자동화 ROI가 높은 유형부터 순차 전환.
  • 수동 요청을 배치 자동화 또는 셀프서비스 어드민으로 전환. 데이터 보정 요청은 Spring Batch Job으로, 설정 변경 요청은 어드민 UI 셀프서비스로 전환. SQS 이벤트 기반 트리거로 요청 접수 → 자동 처리 파이프라인 구축.
  • EventBridge 스케줄 배치로 주기적 운영 작업 자동화. 정기적으로 발생하는 운영 작업(리포트 생성, 상태 동기화 등)을 스케줄 배치로 전환하여 티켓 발생 자체를 제거.
  • Ticket frequency analysis by type and automation target selection. Classified 6 months of tickets by category to identify the top recurring types. Prioritized conversion by automation ROI.
  • Converted manual requests to batch automation or self-service admin. Data correction requests became Spring Batch Jobs; configuration change requests became self-service admin UI flows. Built a request-intake → automatic-processing pipeline using SQS event-based triggers.
  • EventBridge scheduled batches for periodic operational tasks. Converted recurring operational work (report generation, status synchronization, etc.) to scheduled batches, eliminating ticket creation at the source.
  • チケット類型別発生頻度分析後、自動化対象を選定。 直近6ヶ月のチケットをカテゴリ別に分類し上位反復類型を抽出。自動化ROIの高い類型から順次転換。
  • 手動リクエストをバッチ自動化またはセルフサービスAdminへ転換。 データ補正リクエストはSpring Batch Jobへ、設定変更リクエストはAdmin UIセルフサービスへ転換。SQSイベントベーストリガーでリクエスト受付→自動処理パイプラインを構築。
  • EventBridgeスケジュールバッチで定期運用作業を自動化。 定期的に発生する運用作業（レポート生成、ステータス同期等）をスケジュールバッチへ転換しチケット発生自体を除去。
