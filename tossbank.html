Kafka 이벤트 소싱 + Saga 패턴 기반 결제·정산 파이프라인 재설계

  • 문제: 월 100만 건 이상의 충전 완료 건을 처리하는 결제 시스템에서 3초 주기 스케줄러가 충전 완료 건을 읽어 6개 결제 수단 차감, 시간 기반 보류 상태 전이, 재청구, 정산 집계까지 한 흐름에서 수행했습니다. 결제·정산 규칙이 단일 Java+MyBatis 오케스트레이터와 SummaryContext에 누적되어, 정책 변경 시 영향 범위가 넓고 실패 건 추적과 재처리 판단이 느렸습니다.
  • 해결: 3초 폴링을 Kafka 이벤트 소싱(충전 완료 → 결제 → 정산 토픽 체인)으로 전환하고, Transactional Outbox 패턴으로 이벤트 발행의 원자성을 보장했습니다(CDC는 DB 변경 로그 의존으로 스키마 변경에 취약해 Outbox를 선택). 6단계 결제를 Saga 패턴으로 오케스트레이션해 중간 실패 시 Kafka 보상 이벤트로 자동 롤백. Redis Streams 기반 우선순위 큐로 실패 건을 심각도별 자동 분류·재처리하고, Kafka Streams 윈도우 조인으로 정산 정합성 검증(reconciliation)를 준실시간 처리해 감지 지연을 수 시간에서 수 초로 단축했습니다.
  • 결과: Kafka 이벤트 소싱으로 폴링 기반 지연·누락을 원천 제거하고, Saga + Transactional Outbox로 분산 트랜잭션 정합성을 보장하며, Kafka Streams 준실시간 정합성 검증로 장애 추적성과 재청구 정합성을 높였습니다.

  • 문제: 크레딧 일괄 충전이 동기 단일 트랜잭션으로 처리되어 1시간 이상 소요됐고, 처리 중 잔액 정합성 검증 없이 진행되어 부분 실패 시 롤백 범위를 특정하기 어려웠습니다.

Split Payment Saga 오케스트레이션 — 6단계 순차 차감과 Kafka 보상 이벤트

  • 문제: 무상 크레딧 → B2B 크레딧 → 마일리지 → 파트너 포인트 → 신용카드(Nicepay PG) → 포인트 적립 순서의 결제 로직이 단일 메서드에 하드코딩되어 있었고, 중간 단계 실패 시 이전 차감 건의 보상 트랜잭션이 없어 부분 결제 상태가 남을 수 있었습니다.
  • 해결: 각 결제 수단을 Saga 패턴의 독립 스텝으로 분리하고, 중간 단계 실패 시 Kafka 보상 이벤트로 이전 차감 건을 자동 롤백. Redis 멱등성 키로 단계별 중복 실행을 방지하고, Transactional Outbox로 이벤트 발행의 원자성을 보장했습니다. 결제 단계를 플러그인 구조로 설계해 신규 결제수단 추가 시 스텝 모듈 하나만 구현하면 Saga에 자동 등록.
  • 결과: 결제 수단 추가 시 수정 범위를 스텝 모듈 1개로 한정하고, Saga 보상 이벤트로 부분 결제 잔류를 원천 방지했습니다. 단계별 처리 시간·실패율을 Kafka Streams로 실시간 모니터링.
