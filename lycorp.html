문제 Problem 課題

13개 이상의 서비스가 각자 벤더 API를 직접 호출하는 구조로, 채널 추가·벤더 변경 시 전 서비스 수정이 필요. 발송 실패에 대한 감지·재처리 체계가 없어 누락 건을 수동으로 확인해야 했고, 발송 현황에 대한 통합 가시성도 부재.

Over 13 services each called vendor APIs directly, requiring changes across all services whenever a channel was added or a vendor changed. There was no detection or retry mechanism for delivery failures — missed messages had to be checked manually — and no unified visibility into delivery status.

13以上のサービスがそれぞれベンダーAPIを直接呼び出す構造で、チャネル追加・ベンダー変更時に全サービスの修正が必要。配信失敗の検知・再処理体制がなく漏れを手動確認する状態で、配信状況の統合的な可視性も不在。

해결 과정 Solution 解決プロセス

  • 멀티모듈 채널 어댑터로 벤더 의존 제거. 벤더 연동을 채널 어댑터 모듈로 분리하고, 13개 서비스 팀과 공통 계약을 사전 합의한 뒤 SDK로 묶어 GitHub Packages로 배포. 사용 가이드·예제·호환 정책을 함께 문서화해 각 팀이 자력으로 마이그레이션할 수 있도록 지원하고, 서비스 코드에서 벤더 의존성을 완전 제거.
  • 지연 발송 감지 및 자동 재처리. 스케줄러가 RECEIVED/PROCESSING 상태의 임계시간 초과 건을 주기적으로 탐지하고, retry_count 기준으로 지수 백오프 재발송 또는 최종 실패 처리. DLQ 유입 메시지도 재처리 대상에 포함.
  • CloudWatch 기반 채널별 모니터링·알람. 커스텀 메트릭으로 채널별 발송 성공/실패 건수와 실패율을 발행. 운영팀·각 서비스 담당자와 채널별 차등 임계치(SMS 15%, 알림톡 10% 등)를 사전 합의해 적용하고, 초과 시 CloudWatch Alarm → SNS → Slack·이메일로 자동 알람 발송. 심각도 구분(WARNING/CRITICAL)과 중복 억제(snooze) 로직 적용.
  • 발송 이력·통계 API 및 오디언스 타게팅. 기간·채널·상태·수신자 등 복합 조건 조회, 수동 재발송, 일별/주별/월별 채널별 발송량·성공률·실패 사유 Top N 집계 API를 제공. 오디언스 타게팅 기능으로 데이터 기반 고객 커뮤니케이션 품질을 확보.
  • Multi-module channel adapters to remove vendor dependency. Isolated vendor integrations into channel adapter modules, aligned the shared contract with the 13 service teams up front, and published it as an SDK via GitHub Packages. Shipped usage guides, examples, and a compatibility policy alongside the SDK so each team could migrate themselves, fully removing vendor coupling from service code.
  • Delayed-delivery detection and auto-retry. A scheduler periodically detects RECEIVED/PROCESSING messages exceeding the threshold time, retries with exponential backoff based on retry_count, or marks final failure. DLQ messages are included in the retry scope.
  • CloudWatch-based per-channel monitoring and alerting. Published custom metrics for per-channel success/failure counts and failure rates. Pre-aligned per-channel differentiated thresholds (SMS 15%, AlimTalk 10%, etc.) with the ops team and each service owner; threshold breaches trigger CloudWatch Alarm → SNS → Slack/email. Applied severity levels (WARNING/CRITICAL) and duplicate suppression (snooze) logic.
  • Delivery history/statistics APIs and audience targeting. Provided multi-condition queries (period, channel, status, recipient), manual resend, and daily/weekly/monthly aggregation APIs for volume, success rate, and top-N failure reasons. Audience targeting for data-driven communication quality.
  • マルチモジュールチャネルアダプターでベンダー依存を除去。 ベンダー連携をチャネルアダプターモジュールとして分離し、13サービスチームと共通契約を事前に擦り合わせた上でSDKに集約してGitHub Packagesで配布。利用ガイド・サンプル・互換性ポリシーを併せて文書化し、各チームが自力でマイグレーションできるよう支援しつつ、サービスコードからベンダー依存を完全除去。
  • 遅延配信検知および自動再処理。 スケジューラがRECEIVED/PROCESSING状態の閾値超過件を定期検知し、retry_count基準で指数バックオフ再送または最終失敗処理。DLQ流入メッセージも再処理対象に含む。
  • CloudWatchベースのチャネル別モニタリング・アラーム。 カスタムメトリクスでチャネル別送信成功/失敗件数と失敗率を発行。運用チーム・各サービス担当者とチャネル別差等閾値（SMS 15%、アリムトーク10%等）を事前合意の上で適用し、超過時にCloudWatch Alarm→SNS→Slack・メールで自動アラーム送信。深刻度区分（WARNING/CRITICAL）と重複抑制（snooze）ロジックを適用。
  • 配信履歴・統計APIおよびオーディエンスターゲティング。 期間・チャネル・状態・受信者等の複合条件照会、手動再送、日次/週次/月次チャネル別送信量・成功率・失敗事由Top N集計APIを提供。オーディエンスターゲティング機能でデータ基盤の顧客コミュニケーション品質を確保。

문제 Problem 課題

크레딧 만료 처리가 체계화되지 않아 만료 대상 크레딧이 잔액에 그대로 남아 있는 상태. B2B·무상·유상 크레딧이 각기 다른 유효기간과 만료 정책을 갖고 있어 단일 순차 처리로는 일일 만료 대상 수만 건을 00시 안에 완료할 수 없었고, 금결원 보고 시 낙전수입 인식 시점이 불명확하여 재무 보고 정확성에 리스크 발생.

Credit expiration was not systematized, leaving expired credits sitting in user balances. B2B, free, and paid credits each had different validity periods and expiration policies; sequential processing could not complete tens of thousands of daily expirations by midnight. The timing of windfall revenue recognition was ambiguous during KFTC reporting, creating financial reporting accuracy risk.

クレジット満了処理が体系化されておらず、満了対象クレジットが残高にそのまま残っている状態。B2B・無償・有償クレジットがそれぞれ異なる有効期間と満了ポリシーを持ち、単一順次処理では日次満了対象数万件を0時内に完了できず、金決院報告時の雑収入認識タイミングが不明確で財務報告の正確性にリスクが発生。

해결 과정 Solution 解決プロセス

  • SQS + EventBridge Scheduler로 만료 배치 트리거 구축. EventBridge Scheduler가 매일 00시에 SQS로 만료 처리 이벤트를 발행하고, 애플리케이션이 SQS 메시지를 수신해 만료 Job을 실행. 서비스 장애 시에도 SQS 메시지가 보존되어 재기동 후 자동 재처리되며, 수동 크론 관리를 완전히 제거.
  • 가상 쓰레드 기반 유형별 병렬 처리 + 배치 슬라이스 루프. B2B·무상·유상 각 유형을 가상 쓰레드(Virtual Thread)로 동시에 실행해 유형 간 데이터 간섭 없이 병렬 처리. 각 유형 내부는 배치 슬라이스 단위로 조회·만료 상태 전환·이력 저장을 하나의 트랜잭션으로 묶고, 슬라이스 간 0.5초 간격을 두어 DB 부하를 분산. 처리할 건이 없을 때까지 루프를 반복하는 구조로, 수만 건 대량 만료도 1~2분 내에 안정적으로 완료. 개별 유형 실패가 다른 유형에 전파되지 않도록 유형별 예외 처리를 격리.
  • 만료 → 낙전수입 계정 전환 로직을 회계 기준과 정합. 재무팀과 유형별 낙전수입 인식 시점을 사전 합의하고, 만료 처리와 계정 전환이 하나의 트랜잭션 안에서 원자적으로 실행되도록 설계. 건별 감사 로그를 기록해 금결원 보고 시 건별 추적 가능한 데이터 체계를 확보.
  • SQS + EventBridge Scheduler for expiration batch triggers. EventBridge Scheduler publishes an expiration event to SQS daily at midnight; the application consumes the SQS message and executes the expiration job. SQS message retention ensures automatic reprocessing after service recovery, fully eliminating manual cron management.
  • Virtual-thread-based parallel processing with batch-slice loops. B2B, free, and paid types run concurrently on virtual threads (Java 21) with no cross-type data interference. Within each type, a loop queries, transitions, and persists history in one transaction per slice, with a 500 ms pause between slices to spread DB load. The loop repeats until no records remain, completing tens of thousands of expirations reliably in 1–2 minutes. Per-type exception handling is isolated so a failure in one type does not propagate.
  • Aligned expiration → windfall revenue transfer with accounting standards. Pre-agreed per-type recognition timing with the finance team and designed expiration and account transfer to execute atomically within a single transaction. Per-item audit logs ensure record-level traceability for KFTC reporting.
  • SQS＋EventBridge Schedulerで満了バッチトリガーを構築。 EventBridge Schedulerが毎日0時にSQSへ満了処理イベントを発行し、アプリケーションがSQSメッセージを受信して満了Jobを実行。サービス障害時もSQSメッセージが保持され再起動後に自動再処理、手動cron管理を完全排除。
  • 仮想スレッドベースのタイプ別並列処理＋バッチスライスループ。 B2B・無償・有償の各タイプを仮想スレッド（Virtual Thread、Java 21）で同時実行しタイプ間のデータ干渉を排除。各タイプ内部はバッチスライス単位で照会・満了状態遷移・履歴保存を1トランザクションにまとめ、スライス間に500ms間隔を置きDB負荷を分散。処理対象がなくなるまでループを繰り返す構造で、数万件の大量満了も1〜2分で安定完了。個別タイプの失敗が他タイプへ伝播しないようタイプ別例外処理を隔離。
  • 満了→雑収入勘定振替ロジックを会計基準と整合。 財務チームとタイプ別の雑収入認識時点を事前合意し、満了処理と勘定振替が単一トランザクション内で原子的に実行される設計。件別監査ログを記録し金決院報告時に件別追跡可能なデータ体系を確保。

크레딧·마일리지 API 설계 및 개발 Credit & Mileage API Design and Development クレジット・マイレージAPI設計・開発 Spring Boot, JPA, QueryDSL

문제 Problem 課題

크레딧 적립·사용·차감 처리 시 동시 요청에서 잔액 정합성이 깨지는 케이스가 간헐적으로 발생. 기간·유형·상태 등 복합 조건 이력 조회의 응답 속도가 느려 운영 효율에 병목.

Intermittent balance inconsistencies occurred when concurrent requests hit the credit earn/use/deduct flow. History lookups with complex conditions (period, type, status) were slow, creating an operational bottleneck.

クレジットの付与・使用・差引処理で同時リクエストにより残高整合性が崩れるケースが散発的に発生。期間・種別・状態等の複合条件履歴照会の応答速度が遅く運用効率にボトルネック。

해결 과정 Solution 解決プロセス

  • 비관적 락 + 트랜잭션 경계 재설계로 잔액 정합성 확보. 기존 낙관적 락은 충돌 시 재시도 로직이 누락된 상태에서 잔액 불일치를 유발. 적립·사용·차감을 단일 트랜잭션으로 묶고 SELECT FOR UPDATE로 잔액 행을 잠가 동시성 문제를 근본 차단. 분산 락(Redis)은 크레딧 특성상 단일 DB 내 정합성이면 충분하여 운영 복잡도 대비 이점 없음.
  • QueryDSL 기반 동적 조회로 이력 조회 성능 확보. 기간·유형·상태 등 복합 조건 조회가 잦은데, MyBatis 동적 SQL은 조건 조합 폭증 시 XML 유지보수가 어려워 QueryDSL로 전환. 커버링 인덱스와 조합하여 이력 조회 p95 응답속도 개선.
  • Pessimistic locking + transaction boundary redesign to ensure balance consistency. The existing optimistic lock was causing balance mismatches because retry logic was missing on conflict. Wrapped earn/use/deduct in a single transaction with SELECT FOR UPDATE to lock the balance row, eliminating concurrency issues at the root. A distributed lock (Redis) was unnecessary since single-DB consistency was sufficient for credit operations, and would only add operational complexity.
  • QueryDSL-based dynamic queries to improve history lookup performance. Complex condition queries combining period, type, and status were frequent; MyBatis dynamic SQL became unmaintainable as condition combinations grew. Switched to QueryDSL and combined with covering indexes to improve history query p95 response time.
  • 悲観的ロック＋トランザクション境界再設計で残高整合性を確保。 既存の楽観的ロックは衝突時のリトライロジックが欠落しており残高不整合を誘発。付与・使用・差引を単一トランザクションにまとめSELECT FOR UPDATEで残高行をロックし同時性問題を根本的に遮断。分散ロック（Redis）はクレジット特性上、単一DB内の整合性で十分であり運用複雑度に見合うメリットなし。
  • QueryDSLベースの動的クエリで履歴照会性能を確保。 期間・種別・状態など複合条件照会が頻繁で、MyBatis動的SQLは条件組み合わせ増加時にXMLの保守が困難になりQueryDSLへ移行。カバリングインデックスと組み合わせ履歴照会p95応答速度を改善。

정산·결제 배치 시스템 개발 및 운영 Settlement & Payment Batch System Development and Operations 精算・決済バッチシステム開発および運用 Java, Spring Boot, MyBatis, Oracle, Nicepay PG

문제 Problem 課題

충전 완료 트랜잭션마다 무상 크레딧·B2B 크레딧·마일리지·파트너 포인트(블루멤버스/레드멤버스)·신용카드(PG)를 순차 차감하는 다단계 결제 파이프라인에서, 회원 유형별 단가 정책·할인·쿠폰·예외 라우팅 규칙이 계속 추가되며 정합성 검증과 장애 추적이 어려워지는 상태.

A multi-step payment pipeline sequentially deducts free credits, B2B credits, mileage, partner points (Blue/Red Members), and credit card (PG) per completed charge. Member-type pricing, discounts, coupons, and exception-routing rules kept accumulating, making consistency verification and failure tracing increasingly difficult.

充電完了トランザクションごとに無償クレジット・B2Bクレジット・マイレージ・パートナーポイント（Blue/Red Members）・クレジットカード（PG）を順次差引する多段決済パイプラインで、会員タイプ別単価ポリシー・割引・クーポン・例外ルーティング規則が増え続け整合性検証と障害追跡が困難な状態。

해결 과정 Solution 解決プロセス

  • 3초 주기 단건 처리 스케줄러로 정합성 우선 설계. 충전 완료 건을 1건씩 순차 처리해 트랜잭션 간 간섭을 원천 차단. 멀티 인스턴스 환경에서 인스턴스별 처리 대상을 분리(MULTI_TYPE)해 중복 처리를 방지.
  • 상태 코드 기반 예외 라우팅. 택시·제네시스·인카페이·픽업앤차지 등 정산 규칙이 다른 거래를 상태 코드로 분류하고, 48시간 미만 보류 건 자동 감지 등 예외 케이스를 파이프라인 진입 전에 분기 처리.
  • 회원 유형별 동적 단가 조정. 가격 인상 시점에 B2B 크레딧 잔액이 있는 현대·제네시스·신한 회원에게 기존 단가를 유지하는 로직, 아파트 프로모션 충전소의 입주민/비입주민 구분 적용, 럭키패스 H 멤버십 할인 등 회원·충전소·시점 조합에 따른 단가를 처리 시점에 동적으로 결정.
  • 순차 차감 결제 파이프라인과 정산 집계. 무상 크레딧 → B2B 크레딧 → 마일리지 → 파트너 포인트 → 신용카드(Nicepay PG) → 포인트 적립 순서로 잔액이 0이 될 때까지 순차 차감. SummaryContext에 각 단계별 차감 내역을 누적해 할인·쿠폰·크레딧·포인트·카드 결제 금액을 건별로 집계.
  • 실패 재처리 및 금액 대사. 스타터 크레딧 실패 건은 최대 3회까지 100ms 간격 재시도 후 최종 실패 처리. 정산 완료 후 산출 금액과 카드 청구 금액 간 차이를 검증하는 대사 로직으로 불일치 건을 자동 분류(정상/이상/검토 필요).
  • 3-second single-record scheduler for consistency-first design. Processes one completed charge at a time to eliminate inter-transaction interference. In a multi-instance environment, each instance processes only its assigned partition (MULTI_TYPE) to prevent duplicate processing.
  • Status-code-based exception routing. Classifies transactions with different settlement rules — taxi, Genesis, Incarpay, Pickup & Charge — by status code, and branches exception cases such as sub-48-hour holds before pipeline entry.
  • Dynamic unit-price adjustment by member type. Preserves previous pricing for Hyundai/Genesis/Shinhan members with remaining B2B credits at the time of a price increase, applies resident/non-resident pricing at apartment promotion stations, and determines Lucky Pass H membership discounts dynamically based on member, station, and timing.
  • Sequential-deduction payment pipeline and settlement aggregation. Deducts in order — free credits → B2B credits → mileage → partner points → credit card (Nicepay PG) → point accumulation — until the balance reaches zero. Accumulates per-step deduction details in a SummaryContext to produce per-transaction settlement breakdowns.
  • Failure retry and reconciliation. Starter credit failures are retried up to 3 times at 100 ms intervals before final failure. Post-settlement reconciliation compares calculated amounts against card-billed amounts and auto-classifies discrepancies (normal / abnormal / needs review).
  • 3秒周期の単件処理スケジューラで整合性優先設計。 充電完了件を1件ずつ順次処理しトランザクション間の干渉を根本的に遮断。マルチインスタンス環境ではインスタンス別処理対象を分離（MULTI_TYPE）し重複処理を防止。
  • ステータスコードベースの例外ルーティング。 タクシー・Genesis・Incarpay・Pickup & Chargeなど精算ルールが異なる取引をステータスコードで分類し、48時間未満保留件の自動検知等の例外ケースをパイプライン進入前に分岐処理。
  • 会員タイプ別の動的単価調整。 価格引き上げ時点でB2Bクレジット残高がある現代・Genesis・新韓会員には旧単価を維持するロジック、マンションプロモーション充電所の入居者/非入居者区分適用、Lucky Pass Hメンバーシップ割引など、会員・充電所・時点の組み合わせに応じた単価を処理時点で動的に決定。
  • 順次差引決済パイプラインと精算集計。 無償クレジット→B2Bクレジット→マイレージ→パートナーポイント→クレジットカード（Nicepay PG）→ポイント積立の順で残高が0になるまで順次差引。SummaryContextに各段階の差引明細を蓄積し、割引・クーポン・クレジット・ポイント・カード決済金額を件別に集計。
  • 失敗再処理および金額対査。 スタータークレジット失敗件は最大3回まで100ms間隔でリトライ後最終失敗処理。精算完了後、算出金額とカード請求金額間の差異を検証する対査ロジックで不一致件を自動分類（正常/異常/要確認）。

チケット数自体が多いのではなく、自動化されていない手作業がチケットとして流入する構造が問題。

해결 과정 Solution 解決プロセス

  • 티켓 유형별 발생 빈도 분석 후 자동화 대상 선정. 최근 6개월 티켓을 카테고리별로 분류하여 상위 반복 유형을 도출. 자동화 ROI가 높은 유형부터 순차 전환.
  • Ticket frequency analysis by type and automation target selection. Classified 6 months of tickets by category to identify the top recurring types. Prioritized conversion by automation ROI.
  • チケット類型別発生頻度分析後、自動化対象を選定。 直近6ヶ月のチケットをカテゴリ別に分類し上位反復類型を抽出。自動化ROIの高い類型から順次転換。

결과 Results 成果

  • 월간 운영 JIRA 티켓 160건 → 35건 (78% 감소)
  • 엔지니어 운영 대응 시간 주 14시간 → 3시간
  • Monthly operational JIRA tickets 160 → 35 (78% reduction)
  • Engineer operational response time 14 hrs/week → 3 hrs/week
  • 月間運用JIRAチケット 160件 → 35件（78%削減）
  • エンジニア運用対応時間 週14時間 → 3時間
